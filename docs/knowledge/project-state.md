## Delivered Capabilities

### Customer Registration (US-001)
- Public REST API endpoint `POST /api/v1/customers` allows new customers to register.
- Request payload: `{"email": "string", "password": "string"}`.
- Response payload: `201 Created` with `Location: /api/v1/customers/{id}` and `{"id": number, "email": "string", "role": "CUSTOMER", "createdAt": "ISO-8601"}`.
- Email is normalized (trimmed + lowercased) and unique (`uq_customer_email`). Duplicate registrations return `409 Conflict`.
- Password complexity validated (12–72 characters, uppercase, lowercase, digit, special symbol). Stored securely as BCrypt hash in `customer.password_hash` (`VARCHAR(60)`).
- All non-registration endpoints remain secured under Spring Security default-deny (`.anyRequest().authenticated()`).

### Customer Login (US-002)
- Public REST API endpoint `POST /api/v1/auth/login` allows registered customers to authenticate.
- Request payload: `{"email": "string", "password": "string"}`.
- Response payload: `200 OK` with `{"id": number, "email": "string", "role": "CUSTOMER"}`.
- Email is normalized (trimmed + lowercased).
- Failed authentication due to non-existent account or wrong password returns sanitized `401 Unauthorized` with `"Invalid email or password"`.
- Authentication against disabled accounts (`enabled = false`) returns `401 Unauthorized` with `"Account is disabled"`.
- Passwords verified against BCrypt hash via `PasswordEncoder.matches()`.

## Known Constraints

- Persistence layer implemented with H2 file-based storage (`jdbc:h2:file:./data/customer-portal`) and DDL validated via `src/main/resources/schema.sql`.
- Session / JWT tokens not yet issued upon login (basic profile response returned; token mechanism deferred).
